The current deployment qualification uses released xcsh provider `15.5.2`. Main passed the deployment gate before preview activation. Branch creation then deployed one preview directly from main, followed by ten concurrent branches with three rapid Terraform description commits each.

| Gate | Result |
| --- | --- |

## Account for DNS propagation

The first preview's managed DNS existed at the authoritative servers while a recursive resolver retained an earlier negative answer. Its original workflow
passed within the ten-minute retry window. Verification now supports a bounded fresh public DNS fallback and connects to the returned public address while
preserving the environment hostname. Live fallback checks passed without changing DNS infrastructure or runner capacity.

## Historical qualification

| Gate | Evidence |
| --- | --- |

| Documentation | English routes, content links, desktop/mobile layouts, and the published content receipt passed. A redundant favicon reference required a shared-theme repair. |

## Resolve the provider default during recovery

The first apply created resources but reported an inconsistent result because the API returned route `http_method = "ANY"` while configuration left the field unset. The explicit `ANY` setting matched the intended behavior. Deployment then succeeded using the retained state; no replacement backend was created.

## Interpret performance measurements

Five zero-change plans were measured for each resource request with the same provider and main configuration:

| Request | Median plan duration | Aggregate CPU throttling | Peak memory |
| --- | --- | --- | --- |
| Ordinary 7 CPU / 24 GiB | 1.489 seconds | 0 | 198 MiB |
| Candidate 1 CPU / 2 GiB | 1.873 seconds | 2.103 seconds | 224 MiB |
| Retained 2 CPU / 2 GiB | 1.486 seconds | 0 | 237 MiB |

All plans returned exit code 0. The 2-CPU candidate preserved plan duration with a smaller scheduling request. This sample qualifies these zero-change plans; it does not establish every provider operation's resource needs.

A fresh correlated lifecycle sample measured warm assignment p95 at 19 seconds, within the 20-second target. Cold assignment has no qualified samples. Representative documentation, lint, provider-build, and mixed-fleet throughput comparisons remain pending in [runner issue 245](https://github.com/f5-sales-demo/self-hosted-runner/issues/245).

The released Super-Linter seed was removed from GitOps after identity verification rejected it and startup exceeded the cold target. Node-group maxima were preserved. Calculated capacity includes node allocatable CPU, memory, pod slots, DaemonSet requests, and 20 percent headroom; existing fleet limits remain subject to workload qualification.

State and recovery archives are private Kubernetes Secrets. Public evidence contains only identities, counts, timings, and outcomes.
